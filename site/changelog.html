Version 0.45.0

27 November 2026Latest

GitHub Copilot CLI joins as a sixth agent, you can pick the interface and code fonts, and reasoning now reads apart from tool calls, with Codex finally showing its thinking.

GitHub Copilot CLI

  • Copilot CLI (1.0.116, over ACP) can be chosen like the other agents: models read from Copilot itself with Auto first, its routing profile (efficiency, balance, intelligence) offered when the model is Auto, tool calls and edits shown like the other CLIs, and a quota gauge that follows the plan’s monthly budget.
  • Not there yet: additional Copilot accounts in Settings, and a page on the website.

Appearance

  • Settings › Appearance › Fonts lets each account choose an interface font and a code font among Google Fonts. The fonts ship with Sillage, so no request leaves the instance and Desktop works offline; a family downloads only once chosen. The terminal follows the code font.

Conversations

  • Reasoning reads as italic prose behind a thin rule instead of a box that looked like a tool call. It unfolds while it is written and folds once the answer starts.
  • Codex sessions now show their reasoning summaries: Sillage never asked for them, so Codex never showed any thinking.
  • Agent browser calls carry the Sillage logo and readable labels instead of a raw MCP tool name.
  • Tool rows show a sub-agent’s effort level and when Read takes a whole large file.
  • Session details give the Claude Code version the session actually runs, which can differ from the installed one after an update, and say whether the account has extra usage or stops at the limit.

Dev-server previews

  • Agents can title the card of each server they start, point it at a specific page, or keep it out of the thread (it stays in the Preview tab), so an API, a worker and a web app no longer share one generic card.
  • A server that stops leaves a line in the thread instead of vanishing. The card can copy the address and make a demo link.

Settings

  • A new Settings › Release notes page lists recent releases, with the installed one and those not installed yet marked. About links to it.

Fixes

  • A message that never reached its CLI, or a CLI that died at launch, no longer leaves the conversation thinking forever; Stop now closes such a turn. A missing working directory is named instead of being reported as a broken binary.
  • Creating a project inside an existing project’s folder (the project/project trap) now warns and offers to add the parent instead.
  • Scheduled tasks, automations and API tasks with Claude wait out API overloads (up to 30 minutes) instead of failing after a few retries. Interactive conversations still fail fast.
  • After a resume, Codex runs every turn in the mode the composer shows, Plan or Default.
  • remove_worktree no longer refuses a worktree an agent has just merged in its shell.
  • Archived projects no longer take requests from other sessions, and the 20-task cap counts only tasks created by agents, so your own schedules cannot lock agents out.
  • Antigravity no longer leaves an untracked skills/system folder in projects.
  • A steered queued message is no longer lost if loading the conversation fails. OpenCode retries when its port is taken at startup.

Agents

  • Targets Claude Code 2.1.332 (SDK 0.3.332) and Codex 0.172.0. With a recent enough Claude Code, MCP servers are passed over the initialize request rather than on the command line, where their secrets were visible to every user of the machine through ps.

Under the hood

  • The session manager, the conversation page and the file explorer are split into smaller modules, the web app gets a unit test harness, and settings sections load on demand, which leaves room under the PWA precache limit.

Server and Desktop editions. Two database migrations (0078, 0079), applied automatically at startup.

Version 0.44.0

26 November 2026

@ mentions now offer folders and work in every project, the composer names its typing shortcuts, and a radio plays from the rail.

Mentions

  • Typing @ now offers folders as well as files. A folder is mentioned as @path/: Enter or a click mentions it, Tab or the row’s chevron opens it to pick something inside (the chevron works on touch screens). Claude Code receives the folder’s listing; Codex and the other CLIs get the path and read it with their tools.
  • Fixed: in a project folder ignored by an enclosing Git repository (for example a dotfiles repository in your home directory), @ answered “No file matches” for everything. Sillage now walks the folder when Git lists nothing, which also fixes the explorer search and the palette there. A failed listing now says so instead of looking like an empty result.

Composer

  • The empty composer lists the prefixes it understands (@ files and folders, @@ sessions, # cards…), and the Insert menu becomes “Shortcuts”, so referencing a session or a card no longer takes a search.

Radio

  • An on/off switch in the rail plays Claude FM in the background; it keeps playing while you navigate. Settings › Personal › Radio lets each account pick another YouTube video or live stream.

Server and Desktop editions. No database migration.

Version 0.43.1

26 November 2026

Dev-server previews now work in Docker and Kubernetes, and Sillage explains how to set them up.

Fixes

  • The preview listener listened on the container’s loopback only, and neither the image, the compose example nor the Helm chart exposed its port: previews could not work in Docker or Kubernetes. It now listens on the same interface as Sillage (SILLAGE_HOST), the image exposes 7318, the compose example publishes it on loopback, and the chart adds the port to its Service with an optional wildcard Ingress for the preview domain (previews.enabled, previews.domain, previews.tls).

Setting up previews

  • Settings › Previews checks the setup: Sillage requests a preview host through your public address and names the first link that fails (DNS, certificate, unreachable server, proxy target, missing pv-* rule, busy preview port), with what to fix.
  • A new guide, docs/previews.md, explains what each edition needs (Desktop works out of the box), why previews need a domain of their own, and gives Caddy, nginx, Docker Compose and Helm setups. Settings and the Preview tab link to it.

Server and Desktop editions. No database migration.

Version 0.43.0

25 November 2026

Agents get a browser you can watch, a choice of which Sillage tools they receive, and the dev servers they start open right inside Sillage.

All notes for v0.43.0

Dev-server previews

  • When an agent starts a dev server, a card above the composer says so, with an Open the preview button. The conversation panel’s Preview tab shows the app, with the port to pick, reload, open in a tab and copy the address. Ports in Services open it too.
  • On Server, each preview gets a host of its own, pv-<id>.<preview domain>, never Sillage’s address, so the app cannot act with your Sillage session. An administrator sets the domain under Settings › Previews and routes its pv-* hosts to the preview listener (main port + 1, or SILLAGE_PREVIEW_PORT); the page shows a Caddy example. Viewers sign in through a one-minute link and only reach ports they see in Services.
  • The app receives requests for localhost:<port>: Vite, Next or Django need no allowed-hosts setup, and hot reload goes through.
  • Demo links (Server): a public address for people without a Sillage account, valid for an hour, a day, a week or 30 days, revocable. It serves the app only while its dev server runs, and asks search engines not to index it.
  • Pick an element: a crosshair highlights what the pointer hovers in the preview; a click adds the element to your message with its page, CSS selector, text, box and HTML.
  • Desktop opens the loopback port directly; off Linux, name the port yourself. Demo links and element picking need Server.

A browser for agents (optional, off by default)

  • Agents of every CLI get browser tools (Playwright MCP, installed on demand from Settings › Agent tools) driving a headless Chromium the daemon starts for their conversation. The machine’s Chrome or Playwright cache is reused, otherwise Sillage downloads one; nothing ships in the releases.
  • Watch the page live in the conversation’s Browser tab, opened from any browser tool call or from the line above the composer, and take over to sign in or pass a challenge, then hand back. Services › Browsers lists every open browser.

Choose the tools agents get

  • Sillage’s own tools come in families (history, board, coordination, automations, worktrees, actions, instructions, project setup) plus the browser. Administrators set instance defaults under Settings › Agent tools or in the first-run agents step; project owners override any family in the project’s Agents tab. A family that is off leaves the session entirely, which shortens the context of Codex, OpenCode, Grok and Antigravity sessions.

Also

  • The session details popover leads with live status, then API-equivalent cost, tool calls and turns, the context window as a gauge and the most used tools.
  • Files, skills and commands attached to a sent message are tinted in its bubble, as in the composer.

Database migrations: 0076 (agent tool families per project) and 0077 (demo links), both additive.

Version 0.41.0

25 November 2026

A command palette that works inside the current project and acts on the open session, a shorter first-run tour, and a guided tour of the interface.

All notes for v0.41.0

Command palette

  • Opened inside a project, the palette searches that project. The project shows as a token before the input. Remove it with Backspace at the start of the field, its ×, or Cmd/Ctrl+K again, which then switches between the project and everywhere without losing what you typed.
  • Tab on a project result searches inside that project. A last row counts the matches elsewhere and widens the search. When the project has nothing, results from the other projects are shown instead.
  • The open session’s actions have their own group: rename, favorite, archive, copy its reference, link or detach a ticket, export, compact, interrupt, continue in another CLI, move, and open a panel tab. Renaming and linking a ticket are asked in the palette itself.
  • Typed text can start a new session (it lands in the draft) or create a ticket. After a ticket, the palette stays open for the next one.
  • Before you type, what waits on you comes first: pending decisions, sessions waiting for an answer, errors you have not seen. Session rows show their live state.
  • > keeps commands, # tickets, / files.
  • Cmd/Ctrl+Enter opens a result in a new tab, or a new window in the desktop app.
  • Results you pick often rise among close matches. This is remembered per browser.

First run

  • The first-run tour asks nothing up front and is shorter. Agents show what is already installed and signed in. Instructions and memory are one step, split into general instructions, project instructions and project memory.
  • The address step no longer saves an address that does not answer, which could lock an administrator out.
  • Sillage Desktop gets a remote-access step (Tailscale Serve), off by default.
  • A short tour of the interface starts on the first conversation: rail, column, agent choice, composer, panel, palette. It runs once per account and replays from Settings > About. Existing accounts are not interrupted.

Projects

  • Project settings are one click away: a Settings line in the project column, the column’s avatar, and the rail’s context menu.
  • The instructions button and dialog say where a project’s instructions live: kept by Sillage, or the repository’s AGENTS.md / CLAUDE.md. Changing the mode moves to its own dialog.

Fixes

  • The side panel no longer takes keyboard focus from a dialog opened while a page loads.

Available in both Server and Desktop editions. No database migration.

Version 0.40.0

OpenCode 2 support, readable workflow agents, and a clearer view of what sub-agents are doing.

All notes for v0.40.0

OpenCode 2

  • Sillage now installs OpenCode 2 (@opencode/cli 2.4.1) as its managed OpenCode and still works with 1.x. The version is detected when a conversation starts.
  • Sub-agents and background shells can be followed and stopped from the Agents panel, with live shell output. Library skills and sessions started outside Sillage are supported too.
  • The first start of OpenCode 2 migrates its local session database in place. The Versions page explains this before you upgrade.

Sub-agents and workflows

  • Workflow agents (Claude Code) can now be opened from the Agents panel. Their threads are read from the transcripts Claude Code writes and update every few seconds while they run. Finished workflows stay reachable from their card.
  • The sub-agent thread now ends with the same activity indicator as a conversation, and shows a short status line Claude writes about each running sub-agent.
  • A sub-agent launched in the background can be stopped on its own from its thread.
  • When a sub-agent leaves a command running in the background, its completion now appears in that sub-agent’s thread instead of the main one.
  • Activity tiles show the end of the main thread even while a sub-agent is busy. Before, a tile could show a single card.

Session context

  • The list of neighboring sessions, plus the title, card and image reminders, now go with the first message of each launch instead of the system prompt. Claude keeps the first system prompt when a session is resumed, so this list used to stay frozen. OpenCode no longer loses its prompt cache every turn.

Available in both Server and Desktop editions. No database migration. Workflows started before this version do not record their agents’ ids, so their threads cannot be opened.

Version 0.38.0

21 November 2026

Benchmarks made for publishing comparisons, sessions that can reach your other projects, and a pass on robustness: Sillage now keeps running, and keeps its data straight, when something goes wrong.

All notes for v0.38.0
  • Benchmarks.
    • Presets and lineups. Save a lineup with its run settings and comparisons as a preset, order the variants, compare any two or more models side by side, and present the results as a slideshow. Variants carry short public model names.
    • Follow-ups. A finished run accepts another prompt in the same session. Its measures add up and the run is marked as followed up, on the share page and in slides too.
    • Comments. Write what you think of a result, with or without stars. Comments can appear on share pages and slides when you choose to include them.
    • Working time. Durations count working time only: waiting for your answer or sitting idle between turns no longer counts. Wall time is kept beside it, and a run waiting for an answer shows up in Activity, in the rail and on its benchmark page.
    • Every run setting (repetitions, concurrency, duration) can change after launch. The benchmark list is the navigation column, and measures sit on one line per variant.
  • Sessions that act on your other projects. A new project setting, off by default, lets its sessions read and act on the account’s other projects: history, cards, sessions, session references. When it is off, the agent tells you the setting exists. A work_log tool sums time spent per day and project.
  • Agents pane. Background shells unfold onto what they print (Claude Code).
  • Rail. Add projects to the rail from a “+” beside it; the projects dialog is redesigned.
  • Scheduled tasks tell their owner when they start failing: failed launches, failed or timed-out checks, and runs that failed or ran out of time. The notification can be turned off on its own.
  • Robustness.
    • A failing background job is logged instead of stopping the server; a stalled event loop and ignored configuration keys are reported.
    • One server per database: a second Sillage on the same data directory refuses to start instead of sharing it.
    • Shutdown closes every turn in progress, and a Stop pressed while a CLI is still starting takes effect at once instead of sending the message anyway.
    • All five CLIs share one turn lifecycle: a late reply can no longer close the next turn, and a Codex interrupt that never answers no longer leaves the conversation busy.
    • An interface error is contained to the element or page that failed, with a way out, instead of a blank page.
    • Agent requests never run twice across a restart; a worktree is never treated as missing because git failed; board edits survive a GitHub refusal; a checkpoint restoration can be undone; benchmark measures survive a deleted thread.
    • Forks, handoffs and API reads no longer load whole journals into memory.
    • Releases install exactly the dependency tree the tests ran against, and are published only from a commit whose checks pass.
  • Claude model list stays complete across restarts and refreshes.

Database: six additive migrations (benchmark presets and share options, run follow-ups, cross-project setting, agent request claims, reusable worktree names, an index for lifecycle lookups). The last one indexes the events table: on a large database, expect the first start to take a little longer.

Version 0.37.0

16 November 2026

A consumption dashboard that prices every CLI’s tokens at public API rates, benchmark pages you can share, and the wall merged into Activity.

All notes for v0.37.0
  • Consumption, at API prices. A new Consumption entry in the rail shows the tokens your instance processed and what the same work would cost through the public APIs: totals for a period, a chart per day or month by CLI, and one breakdown at a time by CLI, model, project, account or session.
    • Prices come from the public lists of LiteLLM and models.dev, checked daily and on an administrator’s request, so Codex, OpenCode and Antigravity get a cost too. A copy ships with each release for an instance that has not reached the network yet.
    • Prices apply when the page is read: a corrected price also corrects the past. It is an equivalent, not an invoice, and leaves out long-context tiers, priority processing and per-request tools such as web search.
    • Sessions from before the update are read once from their journals at the first start, in the background.
    • Every account sees the whole instance.
  • Benchmarks.
    • Run costs now use the same public prices, so a Codex run and a Claude run compare on the same footing. A model without a public price leaves the cost blank rather than ranking a variant on a partial figure.
    • Redesigned pages: each row of the list is a small scoreboard, and the detail page shows each variant’s page, file or answer side by side, with a layout you choose.
    • Share a benchmark as a standalone page, or download it as a zip with the same page. Public links need Sillage Server with a public URL; Desktop offers the zip.
    • Set how many runs go at once, and change it while runs are pending.
    • Default variant labels name the model that actually answered instead of “default” or an alias.
    • Fixed statistics: cached input and auxiliary models are counted, an unreported cost stays blank instead of reading as free, and Claude’s cumulative costs and overlapping waits are no longer counted twice. Existing benchmarks are repaired.
  • Activity and the wall. The Activity entry now opens the wall with its list beside it: a heading fills the wall with that section, a row brings its tile forward. A new errored filter finds sessions stopped on an error, and a new dialog builds saved views from the filter buttons instead of a query. Tiles are lighter and show their state on the title line.
  • Worktrees and pull requests. Work merged through a GitHub pull request is recognised as merged, with the PR state and checks shown in the worktree views.
  • Reliability. Browser requests from another origin are refused; MCP tool discovery failures are shown; administrators are warned before the host’s Claude login expires; Claude permission choices and MCP removal follow the native CLI.
  • Panel toggle sits at the far right of every header, under the pointer that opened the panel.
  • Supported CLIs: Claude Code 2.1.325, Codex 0.169.0, OpenCode 1.19.5.

Fixed: the stored cost of a Claude conversation added up the CLI’s running total at every turn, so a long conversation showed many times what it had used. Totals are rebuilt from the recorded turns at the first start.

Database: three additive migrations (benchmark concurrency, benchmark shares, turn usage and price lists).

12 November 2026

Sessions stopped by a subscription usage limit can now resume by themselves, and the Claude model selector keeps its full list.

All notes for v0.35.0
  • Resume after a usage limit (#23). When Claude Code or Codex stops a turn on your subscription limit, Sillage tells you once, with the time the limit lifts: push notification, in-app toast, and a visible line in the thread. A session left on “Default” now starts on the model the selector announces (for example Fable 5.1) instead of whatever the CLI picks for that process.

Database: one additive migration (usage_limit_resumes). Desktop edition: no push there, so the limit stop shows as a toast and in the thread.

Version 0.34.2

11 November 2026

Fixes for Sillage Desktop on Windows: installing, starting and quitting.

All notes for v0.34.2
  • “Sillage is already running” while installing. The installer now checks itself what still runs from the installation folder: it waits for a Sillage that is quitting, asks before closing an open one, stops what a closed one left behind, and notes what it did in %LOCALAPPDATA%\Sillage\logs\installer.log.

  • No more blank window while starting. The startup page and the interface show the same mark until the first screen appears.
  • Windows updates are installed from Settings › About, behind a visible installer, and no longer silently when you quit.
  • Exported diagnostics now include startup and stop times.

Updating from an earlier version still goes through the old quit path: close Sillage’s terminals before updating.

Highlights

Sillage Desktop from your other devices

Agents
