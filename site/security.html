Security and privacy

Sillage runs coding agents that read and change files on a machine you own. Here is what it keeps, what it sends, who can reach it, and where its protection stops.

Checked against the code of v0.45.0 on 27 November 2026.

  • No telemetryNo analytics, usage tracking or crash reports, from the server, the app or the web interface.
  • On your machineProjects, conversations and settings stay in a local database on the computer or server you chose.
  • Your accountsEach agent signs in with your subscription or key and talks to its provider directly. Sillage is not a proxy.

What stays on your machine

Server keeps its data in ~/.local/share/sillage unless you choose another folder. Desktop uses the app’s own data folder.

Back up and restore

Your workspace

Projects, conversations, the board, memory and settings live in a SQLite database, next to attachments, worktrees and logs. There is no built-in backup: copy the data folder as the guide explains.

Agent sign-ins

Each CLI keeps its own sign-in in its own folder, as it does in a terminal. Extra accounts get a folder of their own inside the data folder, except extra Claude sign-ins, which are encrypted in the database.

Secrets

MCP server secrets, Git credentials and extra Claude sign-ins are encrypted with AES-256-GCM, and saved secrets are never sent back to the browser. The key sits in the data folder, readable only by your user: this protects a copied database, not a machine whose disk someone can read.

MCP servers

Secrets reach an agent when its session starts. Recent Claude Code versions and the other CLIs receive their MCP servers over a private channel, not on a command line that other users of the machine could read with ps.

Agent transcripts

The CLIs also keep their own transcripts in their own folders. Deleting a conversation in Sillage leaves those files alone.

What leaves it

Your agents send your prompts and the code they read to their providers, under those providers’ terms, exactly as they would from a terminal. Sillage itself sends nothing about you or your code to its author. These are the requests it makes on its own.

Who can reach it

Server listens on 127.0.0.1, port 7317. Reach it through Tailscale, another VPN or an HTTPS reverse proxy, and never expose that port to the internet directly.

Remote access guide

Accounts on Server

Passwords are hashed with Argon2id. A session is a random token, stored hashed, in an HttpOnly cookie that is Secure over HTTPS, valid 30 days. Changing a password signs out the account’s other sessions. There is no two-factor authentication yet.

Requests

Five sign-in attempts per minute per address, then a pause. A request that changes something, or opens a live connection, must come from Sillage’s own origin.

API keys

Scoped to projects, tasks, autonomous tasks or MCP. A key can also be limited to some projects, models or a budget, and given an expiry date. Shown once, stored hashed, revocable. A key cannot create another key.

Desktop

Listens on 127.0.0.1 only and opens its window with a session handed over at launch: no password exists. Remote access is off by default; through Tailscale, it admits only the devices of the account that owns the machine.

Who decides

Administrators own the instance-wide configuration, a project’s owner owns that project’s, and members work in a shared project without changing it.

What agents can do

Agents and terminals run as the system user that runs Sillage, with that user’s files and network. Sillage shows and controls what they do; it is not a sandbox.

Asking first

No CLI starts with approvals off. Each begins in a mode that asks before acting, or, for Codex, works inside the workspace and asks before going beyond it. Modes that allow everything are a choice the conversation’s owner makes, or a project’s owner for its presets.

Agents starting agents

A session that starts another one cannot give it wider permissions, and an API key needs the autonomous tasks scope to run without approvals.

Containing a task

Give a task its own worktree so it works on its own branch, and turn on checkpoints to put files back as they were before a turn.

Shared servers

Server accounts are meant for people you trust. Every agent runs under the same system account, so accounts separate projects and settings, not files. Do not host people you would not give a shell to.

Previews and public links

Previews show what an agent is building, inside Sillage. Demo links and shared conversations show it to people without an account: both need Server, and you can revoke either at any time.

Dev-server previews

Each preview gets a host of its own, never Sillage’s, so the app you preview never receives your Sillage session. Viewers sign in through a link valid for one minute. Desktop shows previews from the computer’s loopback address.

Demo links

A public address for a running preview, valid for an hour, a day, a week or 30 days, revocable, and marked so search engines leave it out.

Shared conversations

A static snapshot. Tool inputs and outputs stay out unless you add them, images are reviewed one by one, and a scan masks secrets, email addresses, IP addresses and home paths before anything is published. Links expire after 30 days by default; revoking one deletes the file.

Releases and updates

Every release is built by GitHub Actions from a tagged commit, once tests, type checks, lint and the build pass on it.

Changelog

Desktop

Checks GitHub at launch and every four hours, and checks each download against the checksum published with its release. The packages are not code-signed or notarized yet, which is why macOS and Windows warn on first launch.

Server

Updates from Settings › About or by running the installer again, and keeps the two previous versions on disk. The installer checks Node.js against its official checksums.

The installer

One shell script you can read before running it. It checks the system and the tools it needs, installs into Sillage’s folder and registers a user service with systemd or launchd. On Linux it turns on lingering, so Sillage keeps running after you log out.

Report a vulnerability

Please report security problems privately rather than in a public issue.

Report a vulnerability Security policy

How

Use GitHub’s private vulnerability reporting on the repository: Security › Report a vulnerability. Describe the problem, how to reproduce it, the version, the edition and the system.

What happens next

Fixes ship in a regular release, and its notes say what was fixed once an update is available. Only the latest release receives fixes.

The rest

Bugs without a security impact, and questions about this page, go to GitHub issues.
