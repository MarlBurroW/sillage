Sécurité et confidentialité

Sillage fait tourner des agents de code qui lisent et modifient des fichiers sur une machine qui t’appartient. Voici ce qu’il garde, ce qu’il envoie, qui peut y accéder, et où s’arrête sa protection.

Vérifié par rapport au code de la v0.45.0 le 27 novembre 2026.

  • Aucune télémétriePas d’analytics, de suivi d’utilisation ni de rapports de plantage, que ce soit depuis le serveur, l’app ou l’interface web.
  • Sur ta machineLes projets, les conversations et les réglages restent dans une base de données locale, sur l’ordinateur ou le serveur que tu as choisi.
  • Tes comptesChaque agent se connecte avec ton abonnement ou ta clé et communique directement avec son fournisseur. Sillage n’est pas un proxy.
  • Open sourceSous licence MIT. Tout ce qui figure sur cette page peut se vérifier dans le code.

Ce qui reste sur ta machine

Server garde ses données dans ~/.local/share/sillage, sauf si tu choisis un autre dossier. Desktop utilise le dossier de données propre à l’app.

Sauvegarder et restaurer

Ton espace de travail

Les projets, les conversations, le board, la mémoire et les réglages se trouvent dans une base de données SQLite, à côté des pièces jointes, des worktrees et des journaux. Il n’y a pas de sauvegarde intégrée : copie le dossier de données comme l’explique le guide.

Connexions des agents

Chaque CLI garde sa propre connexion dans son propre dossier, comme il le fait dans un terminal. Les comptes supplémentaires ont chacun leur propre dossier dans le dossier de données, sauf les connexions Claude supplémentaires, qui sont chiffrées dans la base de données.

Secrets

Les secrets des serveurs MCP, les identifiants Git et les connexions Claude supplémentaires sont chiffrés avec AES-256-GCM, et les secrets enregistrés ne sont jamais renvoyés au navigateur. La clé se trouve dans le dossier de données, lisible uniquement par ton utilisateur : cela protège une base de données copiée, pas une machine dont quelqu’un peut lire le disque.

Serveurs MCP

Les secrets parviennent à un agent au démarrage de sa session. Les versions récentes de Claude Code et les autres CLI reçoivent leurs serveurs MCP par un canal privé, et non sur une ligne de commande que les autres utilisateurs de la machine pourraient lire avec ps.

Transcripts des agents

Les CLI gardent aussi leurs propres transcripts dans leurs propres dossiers. Supprimer une conversation dans Sillage ne touche pas à ces fichiers.

Ce qui en sort

Tes agents envoient tes prompts et le code qu’ils lisent à leurs fournisseurs, selon les conditions de ces fournisseurs, exactement comme ils le feraient depuis un terminal. Sillage lui-même n’envoie rien sur toi ni sur ton code à son auteur. Voici les requêtes qu’il fait de lui-même.

Qui peut y accéder

Server écoute sur 127.0.0.1, port 7317. Accède-y par Tailscale, un autre VPN ou un reverse proxy HTTPS, et n’expose jamais ce port directement sur Internet.

Guide de l’accès distant

Comptes sur Server

Les mots de passe sont hachés avec Argon2id. Une session est un jeton aléatoire, stocké sous forme hachée, dans un cookie HttpOnly qui est Secure en HTTPS, valable 30 jours. Changer un mot de passe déconnecte les autres sessions du compte. Il n’y a pas encore d’authentification à deux facteurs.

Requêtes

Cinq tentatives de connexion par minute et par adresse, puis une pause. Une requête qui modifie quelque chose, ou qui ouvre une connexion en direct, doit provenir de l’origine même de Sillage.

Clés API

Limitées par portée aux projets, aux tâches, aux tâches autonomes ou au MCP. Une clé peut aussi être restreinte à certains projets, à certains modèles ou à un budget, et recevoir une date d’expiration. Affichées une seule fois, stockées sous forme hachée, révocables. Une clé ne peut pas créer une autre clé.

Desktop

N’écoute que sur 127.0.0.1 et ouvre sa fenêtre avec une session transmise au lancement : il n’existe aucun mot de passe. L’accès distant est désactivé par défaut ; par Tailscale, il n’admet que les appareils du compte propriétaire de la machine.

Qui décide

Les administrateurs ont la main sur la configuration de toute l’instance, le propriétaire d’un projet sur celle de ce projet, et les membres travaillent dans un projet partagé sans le modifier.

Ce que les agents peuvent faire

Les agents et les terminaux tournent sous l’utilisateur système qui exécute Sillage, avec les fichiers et le réseau de cet utilisateur. Sillage montre et contrôle ce qu’ils font ; ce n’est pas un bac à sable.

Demander d’abord

Aucun CLI ne démarre avec les approbations désactivées. Chacun commence dans un mode qui demande avant d’agir ou, pour Codex, qui travaille dans l’espace de travail et demande avant d’aller au-delà. Les modes qui autorisent tout sont un choix que fait le propriétaire de la conversation, ou le propriétaire d’un projet pour ses réglages par défaut.

Des agents qui lancent des agents

Une session qui en lance une autre ne peut pas lui donner de permissions plus larges, et une clé API a besoin de la portée des tâches autonomes pour exécuter sans approbation.

Contenir une tâche

Donne à une tâche son propre worktree pour qu’elle travaille sur sa propre branche, et active les points de reprise pour remettre les fichiers comme ils étaient avant un tour.

Serveurs partagés

Les comptes de Server sont prévus pour des personnes en qui tu as confiance. Tous les agents tournent sous le même compte système, donc les comptes séparent les projets et les réglages, pas les fichiers. N’héberge personne à qui tu ne donnerais pas de shell.

Aperçus et liens publics

Les aperçus montrent ce qu’un agent construit, dans Sillage. Les liens de démo et les conversations partagées le montrent à des personnes sans compte : les deux nécessitent Server, et tu peux révoquer l’un comme l’autre à tout moment.

Aperçus des serveurs de dev

Chaque aperçu a son propre hôte, jamais celui de Sillage, donc l’app que tu prévisualises ne reçoit jamais ta session Sillage. Les personnes qui le consultent se connectent par un lien valable une minute. Desktop affiche les aperçus depuis l’adresse de loopback de l’ordinateur.

Liens de démo

Une adresse publique pour un aperçu en marche, valable une heure, un jour, une semaine ou 30 jours, révocable, et marquée pour que les moteurs de recherche l’excluent.

Conversations partagées

Un instantané statique. Les entrées et sorties des outils restent exclues sauf si tu les ajoutes, les images sont vérifiées une par une, et une analyse masque les secrets, les adresses e-mail, les adresses IP et les chemins du dossier personnel avant toute publication. Par défaut, les liens expirent au bout de 30 jours ; en révoquer un supprime le fichier.

Versions et mises à jour

Chaque version est construite par GitHub Actions à partir d’un commit tagué, une fois que les tests, la vérification des types, le lint et le build passent sur ce commit.

Nouveautés

Desktop

Consulte GitHub au lancement et toutes les quatre heures, et vérifie chaque téléchargement par rapport à la somme de contrôle publiée avec sa version. Les paquets n’ont pas encore de signature de code ni de notarisation, c’est pourquoi macOS et Windows affichent un avertissement au premier lancement.

Server

Se met à jour depuis Réglages › À propos ou en relançant l’installeur, et garde les deux versions précédentes sur le disque. L’installeur vérifie Node.js par rapport à ses sommes de contrôle officielles.

L’installeur

Un seul script shell, que tu peux lire avant de le lancer. Il vérifie le système et les outils dont il a besoin, installe dans le dossier de Sillage et enregistre un service utilisateur auprès de systemd ou de launchd. Sous Linux, il active le lingering, pour que Sillage continue de tourner après ta déconnexion.

Signaler une vulnérabilité

Merci de signaler les problèmes de sécurité en privé plutôt que dans une issue publique.

Signaler une vulnérabilité Politique de sécurité

Comment

Utilise le signalement privé de vulnérabilités de GitHub sur le dépôt : Security › Report a vulnerability. Décris le problème, comment le reproduire, la version, l’édition et le système.

Ce qui se passe ensuite

Les correctifs sont livrés dans une version normale, et ses notes de version disent ce qui a été corrigé une fois qu’une mise à jour est disponible. Seule la dernière version reçoit des correctifs.

Le reste

Les bugs sans impact sur la sécurité, et les questions sur cette page, vont dans les issues GitHub.
