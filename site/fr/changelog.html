Version 0.45.0

27 novembre 2026Dernière

GitHub Copilot CLI arrive comme sixième agent, tu peux choisir les polices de l’interface et du code, et la réflexion se lit désormais à part des appels d’outils, Codex montrant enfin la sienne.

GitHub Copilot CLI

  • Copilot CLI (1.0.116, par ACP) se choisit comme les autres agents : modèles lus auprès de Copilot lui-même avec Auto en tête, son profil de routage (efficacité, équilibre, intelligence) proposé quand le modèle est Auto, appels d’outils et modifications affichés comme pour les autres CLI, et une jauge de quota qui suit le budget mensuel du forfait.
  • Pas encore là : les comptes Copilot supplémentaires dans les réglages, et une page sur le site.

Apparence

  • Réglages › Apparence › Polices permet à chaque compte de choisir une police pour l’interface et une pour le code parmi les Google Fonts. Les polices sont livrées avec Sillage : aucune requête ne quitte l’instance et Desktop fonctionne hors ligne ; une famille ne se télécharge qu’une fois choisie. Le terminal suit la police du code.

Conversations

  • La réflexion se lit en prose italique derrière un filet fin, au lieu d’un encadré qui ressemblait à un appel d’outil. Elle se déplie pendant qu’elle s’écrit et se replie dès que la réponse commence.
  • Les sessions Codex montrent désormais leurs résumés de réflexion : Sillage ne les demandait pas, si bien que Codex n’affichait jamais la moindre réflexion.
  • Les appels au navigateur des agents portent le logo Sillage et des libellés lisibles, au lieu d’un nom brut d’outil MCP.
  • Les lignes d’outil montrent le niveau d’effort d’un sous-agent, et signalent quand Read prend un gros fichier en entier.
  • Les détails de session donnent la version de Claude Code que la session fait réellement tourner, qui peut différer de celle installée après une mise à jour, et indiquent si le compte a de l’usage supplémentaire ou s’arrête à la limite.

Aperçus des serveurs de dev

  • Les agents peuvent donner un titre à la carte de chaque serveur qu’ils lancent, la faire pointer vers une page précise, ou la garder hors du fil (elle reste dans l’onglet Aperçu) : une API, un worker et une app web ne partagent plus une même carte générique.
  • Un serveur qui s’arrête laisse une ligne dans le fil au lieu de disparaître. La carte peut copier l’adresse et créer un lien de démo.

Réglages

  • Une nouvelle page Réglages › Notes de version liste les versions récentes, en marquant celle qui est installée et celles qui ne le sont pas encore. À propos y renvoie.

Correctifs

  • Un message qui n’a jamais atteint son CLI, ou un CLI mort au lancement, ne laisse plus la conversation réfléchir indéfiniment ; « Interrompre l’agent » clôt désormais un tel tour. Un dossier de travail manquant est nommé au lieu d’être signalé comme un binaire cassé.
  • Créer un projet dans le dossier d’un projet existant (le piège project/project) déclenche désormais un avertissement et propose plutôt d’ajouter le dossier parent.
  • Les tâches planifiées, les automatisations et les tâches de l’API qui utilisent Claude attendent la fin des surcharges de l’API (jusqu’à 30 minutes) au lieu d’échouer après quelques tentatives. Les conversations interactives échouent toujours vite.
  • Après une reprise, Codex exécute chaque tour dans le mode qu’affiche le composer, Plan ou Default.
  • remove_worktree ne refuse plus un worktree qu’un agent vient de fusionner dans son shell.
  • Les projets archivés n’acceptent plus les demandes d’autres sessions, et le plafond de 20 tâches ne compte que les tâches créées par des agents : tes propres planifications ne peuvent plus bloquer les agents.
  • Antigravity ne laisse plus de dossier skills/system non suivi dans les projets.
  • Un message en file envoyé pour infléchir le tour n’est plus perdu si le chargement de la conversation échoue. OpenCode réessaie quand son port est déjà pris au démarrage.

Agents

  • Versions ciblées : Claude Code 2.1.332 (SDK 0.3.332) et Codex 0.172.0. Avec un Claude Code assez récent, les serveurs MCP passent par la requête initialize plutôt que par la ligne de commande, où leurs secrets étaient visibles de tous les utilisateurs de la machine via ps.

Sous le capot

  • Le gestionnaire de sessions, la page de conversation et l’explorateur de fichiers sont découpés en modules plus petits, l’app web reçoit un harnais de tests unitaires, et les sections des réglages se chargent à la demande, ce qui laisse de la marge sous la limite de précache de la PWA.

Éditions Server et Desktop. Deux migrations de base de données (0078, 0079), appliquées automatiquement au démarrage.

Version 0.44.0

26 novembre 2026

Les mentions @ proposent désormais les dossiers et fonctionnent dans tous les projets, le composer nomme ses raccourcis de saisie, et une radio joue depuis le rail.

Mentions

  • Taper @ propose désormais les dossiers en plus des fichiers. Un dossier se mentionne sous la forme @path/ : Entrée ou un clic le mentionne, Tab ou le chevron de la ligne l’ouvre pour choisir quelque chose à l’intérieur (le chevron fonctionne sur les écrans tactiles). Claude Code reçoit la liste du contenu du dossier ; Codex et les autres CLI reçoivent le chemin et le lisent avec leurs outils.
  • Corrigé : dans un dossier de projet ignoré par un dépôt Git englobant (par exemple un dépôt de dotfiles dans ton dossier personnel), @ répondait « Aucun fichier ne correspond » pour tout. Sillage parcourt maintenant le dossier quand Git ne liste rien, ce qui corrige aussi la recherche de l’explorateur et la palette dans ce cas. Un listage en échec le dit désormais, au lieu de ressembler à un résultat vide.

Composer

  • Le composer vide liste les préfixes qu’il comprend (@ fichiers et dossiers, @@ sessions, # tickets…), et le menu Insérer devient « Raccourcis » : citer une session ou un ticket ne demande plus de recherche.

Radio

  • Un interrupteur marche/arrêt dans le rail lance Claude FM en arrière-plan ; la lecture continue pendant que tu navigues. Réglages › Personnel › Radio permet à chaque compte de choisir une autre vidéo ou un autre live YouTube.

Éditions Server et Desktop. Aucune migration de base de données.

Version 0.43.1

26 novembre 2026

Les aperçus des serveurs de dev fonctionnent désormais dans Docker et Kubernetes, et Sillage explique comment les mettre en place.

Correctifs

  • Le service d’aperçu n’écoutait que sur le loopback du conteneur, et ni l’image, ni l’exemple compose, ni le chart Helm n’exposaient son port : les aperçus ne pouvaient pas fonctionner dans Docker ou Kubernetes. Il écoute désormais sur la même interface que Sillage (SILLAGE_HOST), l’image expose 7318, l’exemple compose le publie en loopback, et le chart ajoute le port à son Service avec un Ingress générique facultatif pour le domaine des aperçus (previews.enabled, previews.domain, previews.tls).

Configurer les aperçus

  • Réglages › Aperçus vérifie la configuration : Sillage demande un hôte d’aperçu par ton adresse publique et nomme le premier maillon en échec (DNS, certificat, serveur injoignable, cible du proxy, règle pv-* manquante, port d’aperçu occupé), avec ce qu’il faut corriger.
  • Un nouveau guide, docs/previews.md, explique ce dont chaque édition a besoin (Desktop fonctionne sans configuration), pourquoi les aperçus demandent leur propre domaine, et donne des configurations pour Caddy, nginx, Docker Compose et Helm. Les réglages et l’onglet Aperçu y renvoient.

Éditions Server et Desktop. Aucune migration de base de données.

Version 0.43.0

25 novembre 2026

Les agents ont un navigateur que tu peux regarder, tu choisis quels outils Sillage ils reçoivent, et les serveurs de dev qu’ils lancent s’ouvrent directement dans Sillage.

Toutes les notes de la v0.43.0

Aperçus des serveurs de dev

  • Quand un agent lance un serveur de dev, une carte au-dessus du composer le signale, avec un bouton Ouvrir l’aperçu. L’onglet Aperçu du panneau de la conversation montre l’app, avec le choix du port, le rechargement, l’ouverture dans un onglet et la copie de l’adresse. Les ports de Services l’ouvrent aussi.
  • Sur Server, chaque aperçu a son propre hôte, pv-<id>.<preview domain>, jamais l’adresse de Sillage : l’app ne peut donc pas agir avec ta session Sillage. Un administrateur règle le domaine dans Réglages › Aperçus et route ses hôtes pv-* vers le service d’aperçu (port principal + 1, ou SILLAGE_PREVIEW_PORT) ; la page montre un exemple pour Caddy. Chaque personne qui regarde se connecte par un lien valable une minute et n’atteint que les ports qu’elle voit dans Services.
  • L’app reçoit des requêtes pour localhost:<port> : Vite, Next ou Django n’ont besoin d’aucun réglage d’hôtes autorisés, et le hot reload passe.
  • Liens de démo (Server) : une adresse publique pour les personnes sans compte Sillage, valable une heure, un jour, une semaine ou 30 jours, révocable. Elle ne sert l’app que tant que son serveur de dev tourne, et demande aux moteurs de recherche de ne pas l’indexer.
  • Choisir un élément : un réticule met en évidence ce que survole le pointeur dans l’aperçu ; un clic ajoute l’élément à ton message avec sa page, son sélecteur CSS, son texte, sa boîte et son HTML.
  • Desktop ouvre directement le port en loopback ; hors Linux, indique le port toi-même. Les liens de démo et le choix d’un élément demandent Server.

Un navigateur pour les agents (facultatif, désactivé par défaut)

  • Les agents de tous les CLI reçoivent des outils de navigation (Playwright MCP, installé à la demande depuis Réglages › Outils des agents) qui pilotent un Chromium headless que le daemon lance pour leur conversation. Le Chrome de la machine ou le cache Playwright est réutilisé, sinon Sillage en télécharge un ; rien n’est embarqué dans les versions publiées.
  • Regarder la page en direct dans l’onglet Navigateur de la conversation, ouvert depuis n’importe quel appel d’outil de navigation ou depuis la ligne au-dessus du composer, et prendre la main pour se connecter ou passer un challenge, puis la rendre. Services › Navigateurs liste tous les navigateurs ouverts.

Choisir les outils que reçoivent les agents

  • Les outils propres à Sillage se rangent en familles (historique, board, coordination, automatisations, worktrees, actions, consignes, configuration du projet), plus le navigateur. Les administrateurs fixent les réglages par défaut de l’instance dans Réglages › Outils des agents ou à l’étape des agents de la première visite ; les propriétaires de projet peuvent choisir autrement, famille par famille, dans l’onglet Agents du projet. Une famille désactivée disparaît entièrement de la session, ce qui raccourcit le contexte des sessions Codex, OpenCode, Grok et Antigravity.

Et aussi

  • Le popover des détails d’une session s’ouvre sur l’état en direct, puis le coût équivalent API, les appels d’outils et les tours, la fenêtre de contexte sous forme de jauge et les outils les plus utilisés.
  • Les fichiers, skills et commandes joints à un message envoyé sont teintés dans sa bulle, comme dans le composer.

Migrations de base de données : 0076 (familles d’outils des agents par projet) et 0077 (liens de démo), toutes deux additives.

Des retours d’utilisateurs d’OpenCode : un sélecteur de modèle où l’on se repère, et un composer qui montre ce qui part avec ton message.

Toutes les notes de la v0.42.0

Modèles OpenCode

  • Le sélecteur de modèle range les modèles d’OpenCode par fournisseur (GitHub Copilot, Anthropic, OpenCode Go…) sous des titres de section, au lieu d’une seule liste triée par nom où le même modèle apparaissait une fois par fournisseur.
  • Le modèle Auto de GitHub Copilot, qui laisse le routeur de Copilot choisir le modèle de chaque session, ouvre la section Copilot quand ton compte dispose d’un pool Auto.
  • Une section Récents, en haut, liste les derniers modèles que tu as utilisés avec OpenCode. La recherche la laisse de côté, pour que chaque modèle n’apparaisse qu’une fois dans les résultats.
  • Réglages › Défauts des CLI utilise le même panneau avec recherche dès qu’un CLI liste plus de huit modèles : un modèle OpenCode par défaut peut donc s’y choisir aussi.

Composer

  • Les fichiers choisis dans les suggestions @, les skills choisis avec $ et une /command en tête que le CLI connaît sont teintés dans la zone de saisie : teinté veut dire joint. Un chemin tapé à la main reste sans teinte, car il n’est pas envoyé comme fichier.

Disponible dans les éditions Server et Desktop. Aucune migration de base de données.

Version 0.41.0

25 novembre 2026

Une palette de commandes qui fonctionne dans le projet courant et agit sur la session ouverte, une première visite plus courte, et un tour guidé de l’interface.

Toutes les notes de la v0.41.0

Palette de commandes

  • Ouverte dans un projet, la palette cherche dans ce projet. Le projet s’affiche comme un jeton devant le champ. Retire-le avec Retour arrière en début de champ, avec son ×, ou avec un nouveau Cmd/Ctrl+K, qui bascule alors entre le projet et partout sans perdre ce que tu as tapé.
  • Tab sur un résultat de projet cherche dans ce projet. Une dernière ligne compte les résultats trouvés ailleurs et élargit la recherche. Quand le projet n’a rien, ce sont les résultats des autres projets qui s’affichent.
  • Les actions de la session ouverte ont leur propre groupe : renommer, mettre en favori, archiver, copier sa référence, lier ou détacher un ticket, exporter, compacter, interrompre, continuer dans un autre CLI, déplacer, et ouvrir un onglet du panneau. Le nouveau nom et le ticket à lier se saisissent dans la palette elle-même.
  • Le texte tapé peut lancer une nouvelle session (il arrive dans le brouillon) ou créer un ticket. Après un ticket, la palette reste ouverte pour le suivant.
  • Avant toute saisie, ce qui t’attend vient en premier : décisions en attente, sessions qui attendent une réponse, erreurs que tu n’as pas vues. Les lignes de session montrent leur état en direct.
  • > ne garde que les commandes, # les tickets, / les fichiers.
  • Cmd/Ctrl+Entrée ouvre un résultat dans un nouvel onglet, ou dans une nouvelle fenêtre dans l’app de bureau.
  • Les résultats que tu choisis souvent remontent parmi les résultats proches. C’est mémorisé par navigateur.

Premier lancement

  • La première visite ne demande plus rien d’emblée et elle est plus courte. L’étape des agents montre ce qui est déjà installé et connecté. Consignes et mémoire forment une seule étape, découpée en consignes globales, consignes du projet et mémoire du projet.
  • L’étape de l’adresse n’enregistre plus une adresse qui ne répond pas, ce qui pouvait couper l’accès d’un administrateur.
  • Sillage Desktop gagne une étape d’accès distant (Tailscale Serve), désactivé par défaut.
  • Un court tour de l’interface démarre à la première conversation : rail, colonne, choix de l’agent, composer, panneau, palette. Il ne passe qu’une fois par compte et se rejoue depuis Réglages › À propos. Les comptes existants ne sont pas interrompus.

Projets

  • Les réglages du projet sont à un clic : une ligne Réglages dans la colonne du projet, l’avatar de la colonne et le menu contextuel du rail.
  • Le bouton et la fenêtre des consignes disent où vivent les consignes d’un projet : tenues par Sillage, ou dans l’AGENTS.md / CLAUDE.md du dépôt. Le changement de mode passe dans une fenêtre à part.

Correctifs

  • Le panneau latéral ne vole plus le focus clavier d’une fenêtre ouverte pendant le chargement d’une page.

Disponible dans les éditions Server et Desktop. Aucune migration de base de données.

Version 0.40.0

24 novembre 2026

La prise en charge d’OpenCode 2, des agents de workflow lisibles, et une vue plus claire de ce que font les sous-agents.

Toutes les notes de la v0.40.0

OpenCode 2

  • Sillage installe désormais OpenCode 2 (@opencode/cli 2.4.1) comme OpenCode géré, et fonctionne toujours avec la 1.x. La version est détectée au démarrage d’une conversation.
  • Les sous-agents et les shells en arrière-plan se suivent et s’arrêtent depuis le panneau Agents, avec la sortie des shells en direct. Les skills de la bibliothèque et les sessions lancées hors de Sillage sont aussi pris en charge.
  • Le premier démarrage d’OpenCode 2 migre sur place sa base locale de sessions. La page Versions des CLI l’explique avant la mise à jour.

Sous-agents et workflows

  • Les agents des workflows (Claude Code) s’ouvrent désormais depuis le panneau Agents. Leurs fils sont lus dans les transcripts qu’écrit Claude Code et se mettent à jour à quelques secondes d’intervalle pendant qu’ils tournent. Les workflows terminés restent accessibles depuis leur carte.
  • Le fil d’un sous-agent se termine désormais par le même indicateur d’activité qu’une conversation, et affiche une courte ligne d’état que Claude écrit sur chaque sous-agent en cours.
  • Un sous-agent lancé en arrière-plan peut être arrêté seul, depuis son fil.
  • Quand un sous-agent laisse une commande tourner en arrière-plan, sa fin apparaît désormais dans le fil de ce sous-agent plutôt que dans le fil principal.
  • Les tuiles d’Activité montrent la fin du fil principal même quand un sous-agent est occupé. Avant, une tuile pouvait ne montrer qu’une seule carte.

Contexte des sessions

  • La liste des sessions voisines, ainsi que les rappels de titre, de carte et d’image, partent désormais avec le premier message de chaque lancement plutôt que dans le prompt système. Claude garde le premier prompt système à la reprise d’une session, si bien que cette liste restait figée. OpenCode ne perd plus son cache de prompt à chaque tour.

Disponible dans les éditions Server et Desktop. Aucune migration de base de données. Les workflows lancés avant cette version n’enregistrent pas les identifiants de leurs agents : leurs fils ne peuvent pas être ouverts.

Version 0.38.0

21 novembre 2026

Des benchmarks faits pour publier des comparaisons, des sessions qui peuvent atteindre tes autres projets, et une passe de robustesse : Sillage continue désormais de fonctionner, et garde des données cohérentes, quand quelque chose se passe mal.

Toutes les notes de la v0.38.0
  • Benchmarks.
    • Presets et compositions. Enregistrer comme preset une composition avec ses réglages d’exécution et ses comparaisons, ordonner les variantes, comparer côte à côte deux modèles ou plus, et présenter les résultats en diaporama. Les variantes portent des noms de modèle publics et courts.
    • Retours. Un run terminé accepte un nouveau prompt dans la même session. Ses mesures s’additionnent et le run est marqué comme ayant reçu un retour, y compris sur la page partagée et dans les diapos.
    • Commentaires. Écrire ce que tu penses d’un résultat, avec ou sans étoiles. Les commentaires peuvent figurer sur les pages partagées et dans les diapos si tu choisis de les inclure.
    • Temps de travail. Les durées ne comptent que le temps de travail : attendre ta réponse ou rester inactif entre deux tours ne compte plus. Le temps écoulé reste affiché à côté, et un run qui attend une réponse apparaît dans Activité, dans le rail et sur la page de son benchmark.
    • Chaque réglage d’exécution (runs par variante, exécutions simultanées, durée maximale) peut changer après le lancement. La liste des benchmarks est la colonne de navigation, et les mesures tiennent sur une ligne par variante.
  • Des sessions qui agissent sur tes autres projets. Un nouveau réglage de projet, désactivé par défaut, permet à ses sessions de lire les autres projets du compte et d’y agir : historique, cartes, sessions, références de session. Quand il est désactivé, l’agent te dit que ce réglage existe. Un outil work_log additionne le temps passé par jour et par projet.
  • Panneau Agents. Les shells en arrière-plan se déplient sur ce qu’ils affichent (Claude Code).
  • Rail. Ajouter des projets au rail depuis un « + » placé à côté ; la fenêtre des projets est repensée.
  • Les tâches planifiées préviennent leur propriétaire quand elles se mettent à échouer : lancements ratés, vérifications en échec ou hors délai, et exécutions en échec ou qui ont dépassé leur durée. Cette notification peut se désactiver à part.
  • Robustesse.
    • Une tâche de fond en échec est journalisée au lieu d’arrêter le serveur ; une boucle d’événements bloquée et des clés de configuration ignorées sont signalées.
    • Un seul serveur par base de données : un second Sillage sur le même dossier de données refuse de démarrer au lieu de le partager.
    • L’arrêt du serveur clôt chaque tour en cours, et une interruption demandée pendant qu’un CLI démarre encore prend effet aussitôt, au lieu d’envoyer le message malgré tout.
    • Les cinq CLI partagent un même cycle de vie des tours : une réponse tardive ne peut plus clore le tour suivant, et une interruption Codex restée sans réponse ne laisse plus la conversation occupée.
    • Une erreur d’interface reste circonscrite à l’élément ou à la page en cause, avec une porte de sortie, au lieu d’une page blanche.
    • Les demandes des agents ne s’exécutent jamais deux fois, même après un redémarrage ; un worktree n’est jamais tenu pour introuvable parce que git a échoué ; les modifications du board résistent à un refus de GitHub ; la restauration d’un point de reprise peut être annulée ; les mesures d’un benchmark survivent à la suppression d’un fil.
    • Les forks, les transferts entre CLI et les lectures par l’API ne chargent plus des journaux entiers en mémoire.
    • Les versions installent exactement l’arbre de dépendances sur lequel les tests ont tourné, et ne sont publiées que depuis un commit dont les contrôles passent.
  • La liste des modèles Claude reste complète d’un redémarrage ou d’un rafraîchissement à l’autre.

Base de données : six migrations additives (presets et options de partage des benchmarks, retours sur les runs, réglage d’accès aux autres projets, réservation des demandes des agents, noms de worktree réutilisables, un index pour les recherches de cycle de vie). La dernière indexe la table des événements : sur une grande base, attends-toi à un premier démarrage un peu plus long.

Un tableau de bord de consommation qui chiffre les tokens de chaque CLI aux tarifs publics des API, des pages de benchmark à partager, et le mur fondu dans Activité.

Toutes les notes de la v0.37.0
  • La consommation, au prix des API. Une nouvelle entrée Consommation dans le rail montre les tokens traités par ton instance et ce que le même travail coûterait par les API publiques : les totaux d’une période, un graphique par jour ou par mois et par CLI, et une répartition à la fois, par CLI, modèle, projet, compte ou session.
    • Les prix viennent des listes publiques de LiteLLM et de models.dev, vérifiées chaque jour et à la demande d’un administrateur : Codex, OpenCode et Antigravity ont donc eux aussi un coût. Une copie est livrée avec chaque version, pour une instance qui n’a pas encore eu accès au réseau.
    • Les prix s’appliquent à la lecture de la page : un prix corrigé corrige aussi le passé. C’est un équivalent, pas une facture, qui ignore les paliers de long contexte, le traitement prioritaire et les outils facturés à la requête comme la recherche web.
    • Les sessions antérieures à la mise à jour sont lues une fois dans leur journal au premier démarrage, en arrière-plan.

Les consignes vivent désormais dans Sillage et non plus dans des fichiers propres à chaque CLI, et sont injectées dans le prompt système des deux CLI : une partie globale (administrateurs) et une par projet (propriétaire), modifiables depuis les Réglages, la page du projet et l’en-tête d’une conversation. Chaque projet choisit où vivent ses consignes : dans Sillage, qui masque aux agents les CLAUDE.md, CLAUDE.local.md et AGENTS.md de l’espace de travail sans y toucher, ou dans le fichier du dépôt, modifié depuis l’interface. Les projets existants restent sur leur dépôt, avec un import proposé en un clic. Les agents lisent et modifient SILLAGE.md avec les outils MCP read_instructions, edit_instructions et write_instructions.
  • Une mémoire de projet partagée par Claude et Codex. La mémoire automatique de Claude Code passe dans les données de Sillage, un dossier par projet. Claude l’utilise comme la sienne, Codex reçoit l’index au démarrage de la session et écrit avec les outils read_memory, write_memory et delete_memory, et une carte Mémoire sur la page du projet te permet de relire, corriger et supprimer les notes. La mémoire Claude de la racine de l’espace de travail est importée une fois, au premier lancement.
  • Les sessions peuvent lancer des sessions et ouvrir des cartes. Nouveaux outils MCP : start_session lance une conversation Sillage avec une mission qui se suffit à elle-même, en choisissant CLI, modèle et effort, à la racine ou dans un worktree neuf, éventuellement sur une carte ; create_card ouvre une carte « À faire » qui note quelle session l’a ouverte ; list_models liste les catalogues et les valeurs par défaut. Les lancements sont limités à deux niveaux d’enchaînement et à six par session et par heure.
  • Les mises à jour se voient depuis tous les écrans. Quand une nouvelle version est publiée, les administrateurs voient désormais un point sur l’entrée Réglages de la barre latérale, et sur le bouton de navigation au téléphone, et plus seulement dans Réglages › À propos.
  • Installer un skill de skills.sh en une étape. Le bouton d’un résultat de recherche indique désormais « Installer… » et ouvre le catalogue sur ce skill, son SKILL.md prêt à installer ; le dépôt devient une source au passage.

Correctifs

  • Un sous-agent Codex qui reçoit un message après avoir fini ne repasse plus « en cours » pour toujours, ce qui gardait une tâche de fond comptée jusqu’au redémarrage du daemon.
  • Le NODE_ENV du serveur ne fuit plus dans les processus des agents.
  • Le chart Helm vise 0.11.0.

Version 0.10.0

4 octobre 2026

Sillage 0.10.0 donne aux sessions Claude et Codex une bibliothèque de skills partagée, alimentée par des dépôts git, et permet à chaque projet d’avoir une image.

Toutes les notes de la v0.10.0

Nouveautés

  • Une bibliothèque de skills pour Claude et Codex. Sillage garde ses propres skills, globaux ou par projet, et les remet à chaque session comme skills natifs : /name dans Claude, $name dans Codex, déclenchés aussi par leur description. Rien n’est écrit dans ~/.claude ni dans ~/.codex. Les skills se gèrent depuis Réglages › Skills et depuis chaque page de projet : en écrire un, importer une archive .zip ou .skill ou un dossier, ou adopter un skill déjà présent sur la machine, puis le modifier en pleine largeur avec ses fichiers annexes. Les sessions déjà ouvertes prennent en compte les changements, et un réglage par conversation désactive la bibliothèque.
  • Des skills depuis des dépôts git. anthropics/skills et openai/skills sont préconfigurés, et les administrateurs peuvent ajouter tout autre dépôt, y compris privé grâce aux identifiants d’Accès git. Un skill s’installe après lecture de son SKILL.md et de sa liste de fichiers, où les scripts sont signalés, et reste épinglé à son commit. Quand la source avance, la mise à jour se relit sous forme de diff et s’applique à la demande. Les administrateurs peuvent aussi chercher dans skills.sh pour trouver des dépôts.
  • Des images de projet. Un projet peut avoir une image (PNG, JPEG, GIF, WebP ou SVG, jusqu’à 1 Mo), affichée dans la barre latérale, le sélecteur de projets, le panneau d’activité et la page du projet. Les agents en définissent une avec l’outil MCP set_project_image, et reçoivent un rappel tant qu’un projet n’en a pas.
  • Des listes de sessions synchronisées. Une session supprimée, renommée ou déplacée dans un onglet met désormais à jour les autres. Un téléphone qui se réveille vérifie sa connexion et se reconnecte si elle était devenue silencieuse, et un bouton d’actualisation ainsi que le geste « tirer pour actualiser » forcent une resynchronisation.
  • Des longues conversations qui s’ouvrent plus vite. Le replay saute les événements remplacés par des événements ultérieurs, découpe ses pages par taille plutôt que par nombre d’événements, et ne récupère les grosses sorties d’outils qu’à l’ouverture de leur carte.
  • L’apparence suit le compte. Le thème, la palette du code et les curseurs d’apparence sont enregistrés sur le compte, et passent d’un appareil à l’autre.
  • Ultracode comme réglage de session. Les sessions Claude peuvent garder Ultracode actif pendant toute la session, sur les modèles qui acceptent l’effort xhigh.

Correctifs

  • La page de nouvelle session affiche toujours les jauges d’usage, au lieu de les replier.
  • Un fil principal Codex n’est plus pris pour un sous-agent, ce qui laissait la conversation affichée comme en cours.
  • Sur mobile, ouvrir un lien de fichier ne laisse plus le panneau latéral décalé hors de l’écran.

Le site a aussi été refait autour de l’usage quotidien de Sillage.

Mise à jour

Les installations faites avec l’installateur se mettent à jour depuis Réglages › À propos, ou en relançant la commande d’installation. Deux migrations de base de données (images de projet, bibliothèque de skills) s’appliquent au démarrage ; les deux ne font qu’ajouter des tables.

Distribution

Les archives Linux x64 et arm64 sont jointes. L’image Docker multi-architecture est disponible sous ghcr.io/marlburrow/sillage:0.10.0. Le chart Helm de main utilise cette version par défaut ; depuis le tag v0.10.0, passe --set image.tag=0.10.0.

Validation

Typage, lint, build, vérification des bindings Codex et 89 tests serveur réussis. La release a été démarrée sur une base au schéma de production : les deux migrations se sont appliquées, et la version précédente démarrait toujours sur la base migrée. La bibliothèque de skills a été éprouvée avec de vraies sessions Claude et Codex, et dans Chromium avec GitHub et skills.sh.

Version 0.9.0

4 octobre 2026

Sillage 0.9.0 tourne sous Windows via WSL2, et permet aux sessions d’un projet de se coordonner entre elles.

Toutes les notes de la v0.9.0

Nouveautés

  • Windows via WSL2. L’installateur en une ligne fonctionne désormais dans WSL2. Il active systemd quand la distribution ne l’a pas, et ajoute une entrée Sillage au menu Démarrer, et en option à l’ouverture de session Windows, qui garde WSL en marche une fois le terminal fermé et ouvre Sillage dans le navigateur de Windows. Voir le guide WSL2.
  • Plus de prérequis Node.js. Sans Node 22+ dans le PATH, l’installateur télécharge la version LTS actuelle de Node (somme de contrôle vérifiée) sous ~/.local/share/sillage/node, pour le seul service. Le script est aussi lu en entier avant de s’exécuter : un téléchargement tronqué, ou une commande qui lit stdin, ne peut plus exécuter un demi-installateur.
  • Des sessions qui se parlent. Le serveur MCP intégré gagne send_session_message, read_session_messages, notify_when_done et broadcast_session_message, et list_sessions indique la branche et les fichiers modifiés de chaque arbre. Le daemon relaie les messages, la conversation les montre comme venant d’une session, et un échange est mis en attente après six allers-retours pour que deux agents ne puissent pas tourner en boucle.
  • Des reprises Codex plus légères. Reprendre ou forker un fil Codex ne rapatrie plus tout son historique (48 Mo pour un seul fil), ce qui pouvait mettre le daemon à court de mémoire.
  • Liens dans l’aperçu Markdown. Les liens relatifs et les images de l’aperçu de l’éditeur se résolvent depuis le dossier du document, comme sur GitHub, et sont cliquables depuis un panneau de projet.

Mise à jour

Les installations faites avec l’installateur se mettent à jour depuis Réglages › À propos, ou en relançant la commande d’installation. Une migration de base de données (messages entre sessions) s’applique au démarrage.

Distribution

Les archives Linux x64 et arm64 sont jointes. L’image Docker multi-architecture est disponible sous ghcr.io/marlburrow/sillage:0.9.0. Le chart Helm de main utilise cette version par défaut ; depuis le tag v0.9.0, passe --set image.tag=0.9.0.

Validation

Typage, lint, build, vérification des bindings Codex et 47 tests serveur réussis, et migrations appliquées à une base vide. L’installateur WSL2 a été éprouvé de bout en bout dans une machine virtuelle Windows 11 (WSL 3.0.1, Ubuntu 26.04 et 24.04) : installation neuve et relance, systemd désactivé, fermeture du terminal, redémarrage de Windows, installation de Codex depuis l’interface, et désinstallation.
