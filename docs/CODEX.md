# Codex integration

Sillage uses `codex app-server` over stdio. Bindings are generated with
**codex-cli 0.163.0**. The general reference is the
[official App Server documentation](https://learn.chatgpt.com/docs/app-server).
Recent fields, especially `agentMessage.questions`, are checked in the types
generated by the installed binary.

## Questions

- `item/tool/requestUserInput` opens a form and receives an RPC response with the
  exact native ID, either a number or a string. `isBlocking` determines the status;
  when absent, older CLI behavior is preserved.
- `agentMessage.questions` opens a **nonblocking** form. The agent can continue,
  and the question remains answerable after a normal turn completion. The response
  goes through `turn/start`, which can also inject into an active turn.
  Resolution is journaled only after the CLI acknowledges it.
- No choice is submitted automatically. `serverRequest/resolved` expires only the
  corresponding request; several forms can coexist.
- Subagent questions are forwarded to their thread. After the daemon stops, forms
  that remained open are expired, even in an already idle conversation.

Structured questions are also enabled in Default mode through a **thread** override
(`features.default_mode_request_user_input`). A short instruction tells the model
how to use forms. A list of choices written only in prose does not create a form.

## Activities

Messages, proposed plans, work steps, commands, file changes, MCP and dynamic tools,
web searches and results, images, waits, reviews, hooks, and compactions all have a
rendering. Tool outputs and patch changes update during execution. Successive diffs
replace the turn summary.

Subagents have their own activity and thread; completing their turn does not close
the parent's turn. Warnings, model changes, retries, and automatic reviews are
visible. Tokens are counted per turn, including cache, using native counters.

`notification-policy.ts` classifies every known notification: translation, generic
detail, or deliberately ignored duplicate. New events are kept in the journal and
viewable in the thread; their updates replace the same visual marker. Items have
a generic fallback and a TypeScript exhaustiveness check. An unimplemented server
request produces a warning and an explicit RPC error. Rendering a dynamic tool
does not provide client-side execution.

## 0.163.0 compatibility

`thread/readState/changed` is ignored: native read/unread state does not control
Sillage's state. Item-reading and read-state update methods are unused. Concurrent
tools remain tracked by ID, even when outputs interleave and they finish in
reverse order.

On October 17, 2026, the 0.163.0 binary was probed with a signed-in account:
asynchronous and blocking questions, answers, and token counting go through the
real runner. `model/list` returns `gpt-6.1-sol` by default; the catalog is still read
dynamically. Bindings are checked against that same binary, isolated from the
production CLI.

## Steering during a response

Since 0.162.1, `instant_interrupt` is enabled by default: `turn/steer` interrupts
the current response. Probed on October 17, 2026, with 0.163.0 (`gpt-6-astra`),
steer sent during `item/agentMessage/delta`:

1. `turn/steer` responds with `{ turnId }`, the same turn; a few more deltas from the
   interrupted response arrive after acknowledgment.
2. That response **never** gets `item/completed`, and `thread/read` does not keep it.
3. A `userMessage` echo of the steer (`item/started` then `item/completed`), a new
   complete `agentMessage` response, then a single `turn/completed` with `completed` status.

The runner ignores the echo because `steer` already journals the message, so it
appears once. It closes the interrupted response with the text already streamed
when the echo arrives or, failing that, before `turn.completed`. Otherwise, it
would exist in the journal only as deltas, missing from search, CLI handoffs, and
`read_conversation`. A late `item/completed` for the same item would be ignored.
The sequence is replayed in `test/codex-runner.test.ts`; the manual
`pnpm --filter @sillage/server codex:steer-probe` probe captures it on the real CLI
(`--raw` for the raw app-server sequence without Sillage).

## Fork

Forking uses `thread/fork { lastTurnId, excludeTurns }`: the last retained turn,
inclusive, whose native ID can be read from `turn/completed` stored in the
`turn.completed` event's `raw`. `thread/rollback` has been gone since 0.156.0.
Forking at the end of the thread specifies no turn; forking before the first
completed turn is rejected because the branch would have nothing to resume.

## Verification and updates

```sh
pnpm codex:types:check # compare bindings with the installed binary
pnpm test             # RPC transport, runner, questions, and journal replay
pnpm test:codex-ui     # real components, mocked API, desktop and mobile
pnpm typecheck
pnpm build
```

The manual `pnpm --filter @sillage/server codex:probe` probe uses a real Codex
account to ask a question, answer it, and check the model's confirmation. It uses
a short turn, does not run in CI, and accepts `CODEX_BIN` and `CODEX_MODEL` to select
the binary and model. Adding `--blocking` also checks blocking questions in Plan
mode. In Default mode, the CLI may also declare `request_user_input` nonblocking:
`isBlocking` is authoritative, not the tool's name.

To update the protocol: run `pnpm codex:types`, review changes, complete translations
flagged by TypeScript, and align the CLI version in `.github/workflows/ci.yml`.
Codex is not required to build a release from committed bindings.
