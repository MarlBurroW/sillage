# Codex integration

Sillage uses `codex app-server` over stdio. Bindings are generated with
**codex-cli 0.172.0**. The general reference is the
[official App Server documentation](https://learn.chatgpt.com/docs/app-server).
Recent fields, especially `agentMessage.questions`, are checked in the types
generated by the installed binary.

## Questions

- `item/tool/requestUserInput` opens a form and receives an RPC response with the
  exact native ID, either a number or a string. `isBlocking` determines the status;
  when absent, older CLI behavior is preserved.
- `agentMessage.questions` opens a **nonblocking** form. The agent can continue,
  and the question remains answerable after a normal turn completion. The response
  goes through `turn/start`, which can also inject into an active turn.
  Resolution is journaled only after the CLI acknowledges it.
- No choice is submitted automatically. `serverRequest/resolved` expires only the
  corresponding request; several forms can coexist.
- Subagent questions are forwarded to their thread. After the daemon stops, forms
  that remained open are expired, even in an already idle conversation.

Structured questions are also enabled in Default mode through a **thread** override
(`features.default_mode_request_user_input`). A short instruction tells the model
how to use forms. A list of choices written only in prose does not create a form.

## Sandbox network access

Every `turn/start` carries an explicit `sandboxPolicy`, because worktrees created
mid-session must join `writableRoots`. That policy replaces the one in
`config.toml`, network access included. The composer therefore offers a **Network**
setting beside the sandbox (hidden in full access, which has no sandbox):

- **CLI default** (the default): Sillage reads
  `[sandbox_workspace_write] network_access` through `config/read` (with the
  conversation's cwd) when the process starts and applies it. Unset means off,
  Codex's own default. `read-only` has no such key and stays off.
- **Allowed** / **Blocked** force the value, for read only and workspace write.

Probed on 0.172.0: with network access off, `curl` fails to resolve hosts and the
model does not ask to escalate, even with `on-request` approval. The setting
replaces the old `webSearch` field, which drove this flag under a misleading name;
stored values were all `false` and now read as the CLI default. Codex's real web
search (`web_search` in `config.toml`) is not exposed.

## Speed tiers

`model/list` gives each model its `serviceTiers` for the signed-in plan
(`priority`, named Fast, on every model; `ultrafast` on some), with a description
of the extra quota they use. The composer offers a **Speed** setting when the
chosen model has tiers: CLI default, Standard, then the CLI's tiers by name.
Switching to a model without the chosen tier returns to the CLI default.

Every `turn/start` carries `serviceTier`. Probed on 0.172.0: the value applies to
that turn and the following ones, an omitted field keeps the thread's tier, and
`"default"` (like `null`) is standard speed. The CLI default therefore sends
`service_tier` from `config.toml` (read with `config/read`), else `"default"`:
omitting it would leave a tier chosen earlier in the session in force.

## Activities

Messages, proposed plans, work steps, commands, file changes, MCP and dynamic tools,
web searches and results, images, waits, reviews, hooks, and compactions all have a
rendering. Tool outputs and patch changes update during execution. Successive diffs
replace the turn summary.

Subagents have their own activity and thread; completing their turn does not close
the parent's turn. Warnings, model changes, retries, and automatic reviews are
visible. Tokens are counted per turn, including cache, using native counters.

`notification-policy.ts` classifies every known notification: translation, generic
detail, or deliberately ignored duplicate. New events are kept in the journal and
viewable in the thread; their updates replace the same visual marker. Items have
a generic fallback and a TypeScript exhaustiveness check. An unimplemented server
request produces a warning and an explicit RPC error. Rendering a dynamic tool
does not provide client-side execution.

Notices Sillage writes itself carry a `codex_*` code and English text; the web
translates them by code. Texts from Codex (warnings, deprecations, sub-agent
errors) are shown as sent. A sub-agent's warning or error shows its own message
under its name, with retries as information, instead of a generic line. Routine
notifications stay out of the thread: the under-development warning about
`default_mode_request_user_input` (silenced by `suppress_unstable_features_warning`),
`account/updated` unless the plan or sign-in changes, and `thread/goal/cleared`.

## 0.172.0 compatibility

The 0.170–0.172 protocol adds one notification, `thread/search/partial` (results of
`thread/search/stream`, which Sillage never calls: ignored), new terminal error codes
(spending limits per API key, project and organization, `bio_policy`) and
multi-environment `environmentId` fields that Sillage consumes without building.
Turn errors now have translated titles for the spending limits, `rate_limit_exceeded`
and the provider policy codes; the banner still shows the CLI's own message. A
spending limit has no reset time, so the automatic resume after a usage limit does not
apply to it.

0.172 starts optional stdio MCP servers that have a cached tool list at the first
tool call (#62366). Sillage's servers are optional (no `required`), so this was probed
on November 26, 2026 with the downloaded 0.172.0 binary and the host's ChatGPT login:
a stdio server still reported `ready` with its tool when the thread started, on two
consecutive threads, as with 0.163.0, and a real turn (`gpt-6.2-astra`) went through
the MCP approval, the tool call and its result. Approval, interruption and steering
fixes in 0.171 (#61801, #61841, #62066, #61820) need no adapter change.

## 0.169.0 compatibility

The 0.164–0.169 protocol adds image results identified by `fileId`, item lifecycle
timestamps, moderation metadata, account/provider management and native thread
sections. Sillage reads a generated image from `savedPath` when the CLI no longer
returns inline bytes, and retains the path if that file is missing or too large.
New terminal error codes (`model_not_found`, `policy_capacity_unavailable`,
`inference_hook_denied`) have translated explanations. Native section changes are
ignored because Sillage owns its navigation.

`McpServerStatus.toolsError` is preserved separately from connection failure:
the panel can explain a failed tool inventory even after a successful handshake.
Human-command approvals remain disabled as an advertised capability; Sillage does
not claim support for enterprise approvals requiring a human on every call.
Provider setup, account workspace switching, moderation display directives and
item timestamps remain deferred rather than exposed as new controls.

Both Server and Desktop use this adapter. Native checks use a downloaded Linux
0.169.0 executable and an isolated `CODEX_HOME`, without updating the host CLI.
With a local Responses fixture, native checks passed consecutive turns, low/high
effort, fork cutoff, steering during `item/agentMessage/delta`, interruption then
another turn, cold resume and another turn after 62 seconds subscribed but idle.
A separate pass through the real `CodexRunner` confirmed one steered user echo,
the interrupted assistant text retained, a complete following response, one
completed turn and an idle final status (card #36). The manager owns the initial
message echo. A real MCP fixture confirmed a connected server can report
`toolsError` when tool enumeration fails (card #33).

Fixture tests additionally cover permissions, questions and tool translation.
These checks do not use a live OpenAI model or verify Windows/macOS runtime.

## Earlier compatibility

`thread/readState/changed` is ignored: native read/unread state does not control
Sillage's state. Item-reading and read-state update methods are unused. Concurrent
tools remain tracked by ID, even when outputs interleave and they finish in
reverse order.

On October 17, 2026, the 0.163.0 binary was probed with a signed-in account:
asynchronous and blocking questions, answers, and token counting go through the
real runner. `model/list` returns `gpt-6.1-sol` by default; the catalog is still read
dynamically. Bindings are checked against that same binary, isolated from the
production CLI.

## Steering during a response

Since 0.162.1, `instant_interrupt` is enabled by default: `turn/steer` interrupts
the current response. Probed on October 17, 2026, with 0.163.0 (`gpt-6-astra`),
steer sent during `item/agentMessage/delta`:

1. `turn/steer` responds with `{ turnId }`, the same turn; a few more deltas from the
   interrupted response arrive after acknowledgment.
2. That response **never** gets `item/completed`, and `thread/read` does not keep it.
3. A `userMessage` echo of the steer (`item/started` then `item/completed`), a new
   complete `agentMessage` response, then a single `turn/completed` with `completed` status.

The runner ignores the echo because `steer` already journals the message, so it
appears once. It closes the interrupted response with the text already streamed
when the echo arrives or, failing that, before `turn.completed`. Otherwise, it
would exist in the journal only as deltas, missing from search, CLI handoffs, and
`read_conversation`. A late `item/completed` for the same item would be ignored.
The sequence is replayed in `test/codex-runner.test.ts`; the manual
`pnpm --filter @sillage/server codex:steer-probe` probe captures it on the real CLI
(`--raw` for the raw app-server sequence without Sillage).

## Fork

Forking uses `thread/fork { lastTurnId, excludeTurns }`: the last retained turn,
inclusive, whose native ID can be read from `turn/completed` stored in the
`turn.completed` event's `raw`. `thread/rollback` has been gone since 0.156.0.
Forking at the end of the thread specifies no turn; forking before the first
completed turn is rejected because the branch would have nothing to resume.

## Verification and updates

```sh
pnpm codex:types:check # compare bindings with the installed binary
pnpm test             # RPC transport, runner, questions, and journal replay
pnpm test:codex-ui     # real components, mocked API, desktop and mobile
pnpm typecheck
pnpm build
```

The manual `pnpm --filter @sillage/server codex:probe` probe uses a real Codex
account to ask a question, answer it, and check the model's confirmation. It uses
a short turn, does not run in CI, and accepts `CODEX_BIN` and `CODEX_MODEL` to select
the binary and model. Adding `--blocking` also checks blocking questions in Plan
mode. In Default mode, the CLI may also declare `request_user_input` nonblocking:
`isBlocking` is authoritative, not the tool's name.

To update the protocol: run `pnpm codex:types`, review changes, complete translations
flagged by TypeScript, and align the CLI version in `.github/workflows/ci.yml`.
Codex is not required to build a release from committed bindings.
